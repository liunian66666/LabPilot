## 2. P0：上线前必须收口的正确性与安全问题

| 项目 | 当前证据 / 工作内容 | 验收标准 |
| --- | --- | --- |
| 开发登录入口 | `app/api/v1/router.py` 的 `/auth/dev-login` 不校验密码，当前无环境限制。优先删除并排查前端/脚本依赖；若保留，只允许显式开启的本地开发模式，生产不得开启 | 生产及其他非开发环境无法使用该入口获取令牌；正常注册、登录与测试夹具继续工作；仅隐藏 OpenAPI 不算关闭 |
| 生产密钥校验 | 启动时拒绝空值、已知默认 JWT 密钥等不安全配置；Zotero 集成启用时校验 Fernet key 格式及内部令牌。校验必须发生在后台调度和业务访问之前 | 不安全配置启动失败且不输出密钥；合法配置能启动；现有小规模 SQLite 部署不因数据库品牌被强制拒绝 |
| 身份与历史迁移 | 审计 `migrate_dev_to_root_user` 每次启动批量改用户的行为，取消持续重写身份。以版本化的一次迁移明确历史数据归属，先备份、检查唯一键冲突、记录执行结果，失败不静默 | 迁移后重复启动不改数据归属；存在 dev/root 双份配置时显式处理冲突；现有用户、审批、资料和 Zotero 绑定保持正确关联 |
| 对象级授权 | 系统性审计 thread、聊天历史、文件、chunk、报告、任务、审批及集成接口；不仅检查 GET，还检查编辑、删除、恢复执行和检索 | Alice 使用 Bob 的对象 ID 不能读、写、检索或恢复执行，且无副作用；不存在与无权访问对普通接口统一返回 404；审批执行同时校验所属用户与会话 |
| 文件与密钥管理 | 补充适用的 `.gitignore`、脱敏 `.env.example`；检查版本历史、共享日志、镜像与构建上下文是否含密钥，不打印密钥核查 | 敏感文件不进入版本控制或镜像；文档说明环境注入与恢复方式；发现实际泄露才按泄露处置轮换，不能仅因本地 `.env` 是明文就认定已泄露 |

身份选择说明：当前登录令牌和大部分业务以 username 作为身份。此次不为了优化临时切换身份键；若以后支持用户名修改，优先迁移到不可变内部用户 ID，并统一处理业务表、凭证表与 checkpoint 命名空间。不能只改一个查询或直接删掉旧迁移。

## 3. P1：Agent 实习项目的交付门槛

| 项目 | 实施边界 | 验收标准 |
| --- | --- | --- |
| Agent 运行预算 | chat、stream、resume 共用预算配置；显式模型超时与重试、图步数上限、每轮工具/模型调用上限。先按合理上限保护核心场景，不硬编码 12 步；图步数也不等于模型或工具调用次数 | 模型循环、慢调用、工具错误均能停止并返回可理解的失败状态；已发生副作用不因失败而重放；审批 interrupt 不被吞掉 |
| 并发与流式资源控制 | 对聊天增加有界准入、按用户并发限制与资源清理；确定断开连接后的任务策略。先限制当前线程/队列模型，是否转全异步由瓶颈决定 | 超额请求明确拒绝或排队；并发 thread 不串状态；同 thread 并发写入有明确策略；断开后不产生无界队列；进程重启不虚报任务已完成 |
| 限流 | 登录/注册保护与聊天成本配额分别处理；聊天按可信登录身份限流，IP 作为补充；反向代理头只信任配置过的代理 | 爆破登录和高频聊天受到限制；不同正常用户不因共享 IP 被随意混为一人；声明单实例或共享计数的部署边界 |
| 核心链路真实验收 | 固定测试账号、示例纪要与本周进展，运行纪要候选→确认入库→任务/进展→周报→修改→拟信→审批 | 检查数据库最终状态、邮件草稿全文与修改后报告一致、版本冲突、拒绝无外发、重复批准无二次执行；缺日期/邮箱需澄清。先截获邮件；真实外发验收需单独明确授权与受控地址 |
| 重启恢复 | 在生成报告后、待审批时、发送结果不明时分别重启；检查文本、卡片、审批与状态恢复 | 不丢失已持久化业务对象，不自动重发 unknown/sending；历史可见不等于中断执行已恢复，分别验收 |
| 基础 CI | 建立 Git 仓库/远端后执行后端静态检查、离线 pytest、前端 build；按需要增加镜像构建。真实外部服务验收与普通回归分开 | 干净环境可运行；普通 CI 不依赖开发者 `.env`、真实模型或真实 SMTP；遵循现有代码基线增量治理，不把未完成流水线写成已交付 |
| 最小运行保障 | 明确单应用实例/单 worker 调度边界；增加存活与就绪检查、备份恢复说明、依赖超时与关键错误记录 | 备份能在隔离目录恢复并读出示例数据；依赖失败可诊断；healthcheck 不被当成调度锁或数据恢复机制 |
| 演示与说明 | 使用新建演示用户和独立数据库，不清空开发者业务数据；准备步骤、已知限制、个人贡献说明 | 能按说明重复演示一条主链路，并讲清两项故障的定位、修复和证据；真实模型/真实邮件/模拟测试分别标注 |

完成 P0 与 P1 核心链路后即可用于投递。是否录用还取决于基础知识与独立解释、调试能力，不以新增组件数量判定。

## 4. P2：按岗位选择的工程深化

### AI / Agent 应用方向：优先评测与可观测性

- 建立有正确答案与证据的 RAG gold set，覆盖漏召回、无答案、冲突/时间更新、跨用户资料；分别测 recall@k、回答正确性、引用支持度与拒答行为。现有三态契约测试不能替代真实检索评测。
- 扩大跨工具场景评测，记录最终状态、人工澄清与修改、失败回退、每成功任务的模型/工具调用、token、成本和耗时。
- 接入 request_id / run_id 关联 API、模型、工具、审批和后台任务；避免记录凭证与不必要的敏感正文。全局内存计数可用于调试，持久化或结构化日志用于跨重启分析。
- 比较原有人工做法、按钮流和 Agent 流；HTTP 次数不能替代 UI 点击，也不能证明用户总耗时降低。以真实用户试用补充留存与重复使用情况，不预设提升比例。

### 后端方向：选择数据检索或持久任务作为一条深化主线

**PostgreSQL / pgvector / Alembic：** 当前 RAG 仍加载片段并在 Python 计算向量相似度，适合作为优化对象，但不是所有实习项目的必需依赖。

1. 先固定数据规模与查询集，测当前吞吐、p50/p95、内存与检索质量。
2. 引入版本化迁移与 PostgreSQL 集成测试；清理 SQLite 专用 PRAGMA、原始 SQL 的 UUID 表达和事务行为，业务库与 LangGraph checkpoint 存储分别决策。
3. 验证模型维度、向量列与查询一致，再增加合适的索引；1536 不应脱离当前 embedding 模型硬编码。
4. 先在查询中限制用户和文档权限，再进行召回与排序；评估 ANN 在用户过滤后的召回，比较 exact 与 ANN 基线。
5. 根据实测决定何时需要 HNSW；写清数据分布、硬件、并发、过滤条件、构建时间与 recall，不预先承诺“10 万 chunk 毫秒级”。

**持久化入库任务：** 文档状态 pending/indexing/ready/failed，持久保存任务与尝试状态；worker 原子领取，限定并发，记录失败与恢复策略。上传成功与可检索就绪在前端区分。

- embedding 重试与 chunk 写入必须考虑幂等和部分完成，进程退出后能恢复或明确失败；FastAPI BackgroundTasks 或新开线程本身不提供持久任务保证。
- 邮件不能直接套普通自动重试：审批邮件 failed/unknown 不自动重发；提醒仅明确 failed 可重试；unknown/sending 等待核查。发送动作无法仅靠数据库锁获得端到端 exactly-once。
- 多实例时明确唯一调度责任或采用任务队列与租约；`SKIP LOCKED` 只是并发领取的一种机制，不解决崩溃后外部发送结果未知的问题。

### 全栈方向：优先补齐真实交互

在核心验收基础上完善上传进度/失败重试、跨登录历史恢复、周报修改冲突提示、审批状态刷新与断线提示，再验证真实点击与用户任务完成耗时；无需把后端候选项全部实现后才能投递。

## 5. P3：需求成立后再做的扩展

- 课题组 workspace、成员与角色、共享资料及负责人：这是组织协作能力，不等同于已有个人用户隔离。
- 独立调度进程、更多 worker、共享限流、数据库容量优化：根据容量测量逐步推进。
- 通用审批 MCP / 报告 MCP：先有外部调用方再抽取。已有 Zotero MCP 已能证明标准协议接入经验，无需仅为市场标签拆更多服务。
- 审批若对外提供接口，身份必须来自可信鉴权上下文。允许模型发起审批申请、查询受控状态，不得让 Agent 仅凭自己传入的 user_id 或 decision 获得人工批准权限；准备、审批与执行的权限要分离。
- MCP 不要求所有工具都无业务状态；外部接口可以保持无会话依赖，审批、任务与执行记录仍需持久化。contextvars 不是必须删除的机制，关键是值来自可信身份且不跨请求泄漏。
- 上架、英文文档、演示视频有展示价值，但不等于市场需求、用户采用或商业成功。

## 6. 对原方案的修正

| 原建议 | 合并后的判断 |
| --- | --- |
| 生产必须拒绝 SQLite | 拒绝不安全密钥；SQLite 是否保留取决于明确的单实例、小规模运行边界，PostgreSQL 作为独立深化项 |
| 本地 `.env` 明文即证明密钥泄露 | 配置文件本地保存与对外泄露不同；检查共享范围与历史，确认泄露后轮换，不回显密钥 |
| 直接删除 dev→root 迁移并统一用户名 | 先核查旧数据与冲突，以版本化迁移解决身份归属；不破坏既有用户数据 |
| SQLModel 单列查询返回后取 `r[0]` | `session.exec(select(ReminderSetting.user_id))` 返回标量字符串，直接使用；取 `[0]` 会变成用户名首字符，已完成调度采用直接取值 |
| 改 `async def` 就解决阻塞 | 需要端到端 await 或有界线程卸载；仅换函数声明可能把同步调用放进事件循环，造成阻塞 |
| 单 worker 加 healthcheck 即解决调度 | 这是可接受的部署边界，healthcheck 不提供互斥、持久执行或恢复保证 |
| 换 SQL 锁即获得多实例可靠发送 | 并发领取、崩溃恢复、外部副作用不确定性分别处理，保留 unknown 边界 |
| 两个独立 MCP Server 是实习必需或更大市场的证明 | 保留 Zotero 接入亮点；通用化要有实际调用方、权限设计和使用证据 |
| 预估几天即可完成全部改造 | 不承诺固定天数；按阶段验收，尤其数据库迁移和真实端到端链路不能按简单代码替换估时 |
| 先给出“生产化改造”简历 bullet | 等功能交付、测试与运行证据成立后再写；本计划不得被当作已完成经历 |
