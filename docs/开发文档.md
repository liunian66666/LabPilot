# LabPilot 开发文档

> **项目名：** LabPilot（实验室领航 / 课题组科研事务助理）  
> **定位：** 任务型科研助理原型——从组会/材料中**抽出可追溯任务**，维护四维待办与进展，生成**有依据的周报**，外发前**强制人工确认**。  
> **形态：** 个人可演示的全栈服务（API + 简单 Web），非企业 SaaS。  
> **文档状态：** v0.2（吸收评审：主闭环优先、证据链、审批协议、评测前置）  
> **本文与代码同仓演进；改功能请同步 §3 / §12。**

---

## 1. 产品定义

### 1.1 要解决的真实问题（基于读研日常）

| 痛点 | 现象 | LabPilot 的应对 |
| --- | --- | --- |
| 任务易漏、来源模糊 | 组会一句「下周五前补完消融」靠记忆，事后对不清「谁说的、依据是什么」 | 纪要/对话抽任务 → **原文依据** → 待办入库 |
| 资料难找、答案无出处 | 文献/纪要散落，通用模型易编造 | 私有资料库问答，出处必须**支持回答**，否则拒答 |
| 周报缺事实 | 只看「打勾」写不出真实进展与卡点 | **进展记录** + 任务事件 → 可编辑周报草稿 |
| 外发风险 | 给导师/同学的信不能自动乱发；改一个字就该重批 | **审批单绑定内容版本**，拒绝/改稿/重复请求行为可预期 |

### 1.2 一句话定位

> LabPilot：把课题沟通里的「事」变成可追溯任务，用资料与进展生成可信草稿，外发前必须人点头。

### 1.3 非目标

- 通用聊天皮肤 / 全网搜索套壳  
- 企业级中台、多租户 SaaS、虚构客户与使用规模  
- 重流程（报销、权限中心、工单）  
- 一上来做移动端、分布式调度、自动回归平台  
- **不承诺**严格「恰好一次」邮件投递（见 §7.4）

## 2. 用户与场景

**主要用户：** 研究生本人（+ 可选 1–2 名同学试用）。开发期**固定开发身份**，不做完整登录体系（P1）。

### 2.1 主产品主入口：组会纪要 → 任务闭环（P0）

```text
上传组会纪要
  → 提取任务（含原文依据）
  → 补齐/确认缺失信息（日期、交付物、来源）
  → 待办入库（四维 + 证据链）
  → 执行中更新进展
  → 生成周报草稿（引用进展与任务事件）
  → 编辑 → 拟邮件 → 审批 → 批准发送 / 拒绝仅留草稿
```

**示例输入句：**「下周五前补完消融实验，结果给老师看一下。」  
系统需识别：**事项**（补完消融实验）、**相对日期**（下周五）、**交付物**（给老师看结果）、**来源句**（纪要原文片段）；缺失则追问或标「待确认」。

### 2.2 辅助场景（仍做，但服从主闭环）

- 资料问答（有出处 / 无答案 / 冲突）  
- 语言里直接建待办（自然语言 → 四维，缺省可解释）  
- 周报与邮件确认（见上链路后半段）  

### 2.3 连续演示剧本（投递用）

1. 处理一份纪要 → 抽出 3 条任务（带出处）→ 确认 1 条缺失日期后入库  
2. 更新其中 1 条为完成 + 写进展（含观察结果）  
3. 生成本周周报草稿（显示所用记录 ID）  
4. 拟给老师的邮件 → **先拒绝**（不外发）→ 改正文 → **再批准**（发送一次）  
5. 等待审批时重启服务 → 恢复后仍能继续审批流程

```text
     │  Agent 运行时        │       │  业务服务            │
     │  LangGraph           │       │  extract / todo /    │
     │  agent ↔ tools       │       │  progress / report / │
     │  HITL interrupt      │       │  rag / mail-executor │
     └──────────┬──────────┘       └──────────┬──────────┘
     ┌──────────▼─────────────────────────────▼──────────┐

```

### 4.1 模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `services.extract` | 纪要/文本 → 任务候选 + 证据 | 直接入库终态 |
| `services.todo` | 四维、状态、`todo_events`、视图 | 用存储的 today/this_week 判断时间 |
| `services.progress` | 进展条目读写 | 编造实验结果 |
| `services.report` | 区间聚合 → 草稿 + 所用 ID | 自动发送 |
| `services.rag` | 文档/切片、检索、片段拼装 | 把检索内容当工具授权 |
| `services.mail` | 草稿构建、**受控执行器** | 无批准直接 SMTP |
| `agent` | 编排、工具、interrupt/resume | 在工具里绕过执行器 |

| 字段 | 说明 |
| --- | --- |
| id, user_id, title, detail | |
| **due_at** datetime? | 日期事实（推荐） |
| **planned_date** date? | 「今天打算做」但无硬截止 |
| **priority** enum | urgent_important / important / urgent / normal |
| **source** enum | meeting / advisor / paper_ddl / personal / comm |
| **status** enum | todo / doing / waiting / blocked / done / cancelled |
| origin_session_id? | |
| **origin_document_id? / origin_chunk_id?** | 回到纪要/记录 |
| **source_quote?** | 为什么抽出这条任务 |
| confirm_state | confirmed / needs_confirm |
| created_at, updated_at, completed_at | |

**禁止持久化** `time_bucket=today/this_week` 作为事实。  
「今日 / 本周 / 逾期」由 **查询时** 相对 `due_at` / `planned_date` + 当前时区计算。

**日期约定（写进配置与 README）：**

- 时区：`Asia/Shanghai`  
- 周起始：周一 00:00 ～ 周日 23:59  
- 「周五前」默认：当周五 23:59:59（本地）；若相对日已过该周则按下一周解析  
- 仅「下周五」等：解析为 date，时间取当日 23:59:59  
- 解析失败：`due_at=null` + `confirm_state=needs_confirm`，**不瞎填**

| 维 | 存储 | 说明 |
| --- | --- | --- |
| 时间 | `due_at` / `planned_date` | 视图动态算 |

**视图（查询计算）：**

| 视图 | 规则 |
| --- | --- |
| today | `planned_date = today` 或 `due_at` 在今天或已逾期未完成 |
| this_week | due/planned 落在本周一～周日 |

## 7. Agent、工具与邮件审批协议

### 7.1 状态图

```text
START → agent ⇄ tools → END
```

**「图未结束」≠「等人工批准」。**  
待审批判定 = `interrupt` 显式信号（或工具返回的 `approval_id` + `status=pending`），不得仅用 `snapshot.next` 非空当作待审批。

### 7.2 工具与风险

| 工具 | risk | 说明 |
| --- | --- | --- |
| extract_tasks_from_note | read/write | 写候选或待确认任务，带证据 |
| search_knowledge | read | 出处见 §9 |
| list/create/update_todo | write | 可撤销本地写 |
| add_progress | write | |
| draft_weekly_report | write | 存草稿 + source_refs |
| prepare_email | external | 建审批单 + interrupt |
| send_email | external | **仅** mail executor，且校验批准与版本 |

### 7.3 审批恢复协议

**请求：**

```json
{
  "approval_id": "uuid",
  "decision": "approved" | "rejected",
  "payload_version": "sha256-or-int",
  "session_id": "..."
}
```

**服务端校验：**

1. 会话用户 = 审批单 user  
2. approval 存在且可决策（pending）  
3. `payload_version` 与当前一致  
4. **原子更新** `pending → approved|rejected`（乐观锁/单条 UPDATE WHERE status=pending）  

**规则：**

| 场景 | 行为 |
| --- | --- |
| 改 to/subject/body | 旧批准**失效**，新建/更新审批单要求重新确认 |
| 重复批准 | 第二次 409 或幂等返回，**不**二次发送 |
| 并发批准 | 仅一个线程赢得状态迁移 |
| 过期 | deadline 后 `expired`，拒绝执行 |
| 拒绝 | 不调用 SMTP；可改稿再走新一轮 |

**执行器 `send_email`：**

- 只接受 `approved` 且 `payload_version` 匹配  
- 调用前：`approved → sending`（原子）  
- SMTP 成功 → `sent`；明确失败 → `failed`  
- **SMTP 已接受但应用崩溃** → 本地未知：`unknown`，**禁止自动重发**，人工核查  

### 7.4 恰好一次的诚实表述

- 可做：**审批绑定、重复请求防护、发送结果审计**  
- 不可做承诺：严格 exactly-once 投递  
- 简历/面试用语见上句，不说「保证只发一封且必达」  

### 7.5 LangGraph interrupt 幂等

官方语义：恢复中断时可能**从含 `interrupt()` 的节点重入**（[Interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)）。  
因此：审批单创建用**确定性键**（如 `session_id + action_key + payload_version`）做 upsert，禁止重入时重复插单；审计事件允许追加但标注 `reentry=true` 可选。

### 7.6 checkpoint vs 审批单

| | checkpoint | approval |
| --- | --- | --- |
| 职责 | 图执行状态恢复 | 业务是否允许外发 |
| 恢复后 | 继续节点 | 仍须 status=approved + version |
| 异常 | 图可 resume | 执行器最终闸门 |

## 9. RAG：出处必须支持回答

### 9.1 检索结果三态

| 案例 | 预期 |
| --- | --- |
| 有材料但无此指标/事实 | 「资料未提供该指标」+ 相关片段，**不编造** |
| 两次纪要数值冲突 | 并列引用（时间/条件），说明差异，可要求用户裁决 |
| 片段内含指令（「发邮件给…」） | **仅作资料**，不触发工具、不授予外发权限 |

### 9.2 引用展示

回答正文 + `citations[]`：chunk_id、document_id、page_or_section、quote。  
P0 可用 API 返回 quote；P1 点击跳转文件。

## 12. 评测与验收

### 12.1 指标口径原则

> **禁止编造**使用规模、用户数、无测量的「性能提升 x%」。  
> **允许报告**真实测量结果，并注明 **样本量、测试条件、统计口径**。

### 12.2 固定评测集（开发初期即积累，目标约 30 条）

| 类别 | 覆盖 |
| --- | --- |
| 资料问答 | 有答案 / 无答案 / 冲突数值 |
| 任务抽取 | 含相对日期 / 缺日期 / 需确认交付物 |
| 周报 | 有进展可写 / 无记录必须「待补充」 |
| 审批 | 批准 / 拒绝 / 改稿后再批 / 重复批准 / 过期 |
| 恢复 | 等待审批时重启服务后可继续 |
| 故障 | 发送超时 / SMTP 失败 / 结果不明（unknown） |

**确定性规则测试**（无 LLM）：状态迁移、版本校验、动态日期视图、拒绝零 SMTP。  
**模型效果**：抽取/问答逐例对照；可对比「单次提示词」vs LabPilot 链路，保留逐例结果，不要只报均分。

邮件闸门用**模拟执行器**（记录调用次数）验证；真实 SMTP 仅演示可选。

### 12.3 行为验收（硬门禁）

1. 纪要任务可回溯到 `source_quote` + document/chunk  
2. 无 `due_at` 不硬编；今日/本周/逾期由查询计算  
3. 周报不编造无记录结论；保留 `source_refs`  
4. 未批准 / 拒绝 / 版本不匹配 → **零**真实发送  
5. 重复批准不二次发送；改稿后旧批准无效  
6. 等待审批时重启 → 仍能完成同一 approval 流程  
7. 检索无据明确拒答；冲突并列展示

## 13. 里程碑（可演示闭环优先）

> 总日历约两周量级；**先闭环，后铺开**。

| 序 | 可验收成果 | 大约 |
