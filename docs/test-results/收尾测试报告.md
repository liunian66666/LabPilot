## 真实模型中通过的主要行为

- 根据请求生成周报，并返回 report artifact。
- 缺少收件人时没有自行创建邮件审批。
- 通过自然语言修改原周报，修改落库且返回编辑后的 report artifact。
- 指定邮箱后准备邮件，正文与数据库中最新周报全文一致。
- 图确实暂停等待审批，另一个进程可以读取历史及待审批状态。
- 拒绝没有执行发送；批准通过 mock 执行；重复批准没有新增发送。
- 明确重新申请邮件时创建新的审批单。

以上是一次固定场景验收的结果，不是稳定成功率或性能提升指标。

## 阻塞问题：审批恢复重复建单

真实模型验收记录：

- 拒绝后恢复：审批总数从 1 增至 2。
- 新申请获批准后恢复：审批总数从 3 增至 4。
- 接口均返回图恢复成功，因此只检查响应文字会漏掉这一问题。

独立进程复现：第一个进程准备邮件并暂停后退出，第二个进程恢复历史并批准。原单为 sent，但数据库最终出现两张单，状态分别为 sent、pending。

代码原因：`prepare_email_tool` 在 interrupt 前创建审批单，而工具节点要等工具返回后才从 ToolMessage 更新 pending_approval_id。暂停时这个关联尚未写回图状态。恢复重入时，原单已被接口处理为 rejected 或 sent，工具又进入新建分支。force_new=true 也仍作用于恢复重入，无法区分一次新的用户申请和一次旧动作恢复。

建议：在独立的准备节点提交并保存稳定 action/approval ID，再进入只负责等待人工决定的节点。恢复时严格绑定原动作；只有新的用户申请才创建新动作。补端到端回归：批准、拒绝、force_new 重申及进程重启后恢复均不得意外新增审批单。
